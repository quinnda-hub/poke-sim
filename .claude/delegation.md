# Claude Code delegation

This is a standing request to use subagents. Do not wait for me to ask.

This is Claude Code execution guidance, not a second project policy. The project's own instructions (`AGENTS.md`, `CLAUDE.md` and the documents they link) own scope, architecture, testing, independent review, PRs and authorization. A successful subagent report does not authorize further work.

- **Lead/main session keeps:** understanding the request and current branch/PR state, root-cause decisions, scope and architecture, branch setup, diff review, final verification, and acceptance. Stay within the owner's authorization.
- **Reconnaissance (`scoper`):** Run it before planning unless you expect to read 3 or fewer files you have not already read in this session. Treat its brief as input: spot-check the files it cites and do not treat its guesses as decisions.
- **Research (`researcher`):** Use it for outside reference rounds (documentation, papers, talks, footage, photos, how other products behave, measured values). Brief it with the question, the `local/` folder, the sources to cover, the disk cap and the stopping condition. Run parallel lanes as separate researchers with separate folders. Raise the effort in the call when the output is rules or a recommendation.
- **Implementation (`implementer`):** Delegate once the approach is decided and the change spans multiple files or needs more than one edit-test cycle. Edit directly only when the change is small and fully known. Keep work in the lead when it needs unresolved judgment, such as architecture or ownership boundaries, public interfaces, concurrency or determinism, contract and decision changes, or any area this project's `CLAUDE.md` lists as lead-only; resolve or split that uncertainty before delegating. Keep concurrent edits in separate owned files or worktrees.
- **Handoff:** Subagents start with an empty context. Supply the task or issue, acceptance criteria (for tests, name the properties and rules to cover, not enumerated case matrices unless a specific risk justifies one), owned paths and interfaces, relevant existing contracts, decisions already made, edge cases, exact build/test commands, dependencies, and the stopping condition. Ask for concise findings and the exact checks run.
- **After implementation (mandatory):** Do not trust the implementer's summary. Read the diff, compare it with the plan, check callers and tests, look for regressions and weakened tests, and run the relevant checks yourself. Send substantial fixes back to the same implementer with `SendMessage` so it keeps its context. Reconcile conflicts instead of silently expanding scope.
- **Review (`reviewer`):** Use it where the project's independent-review requirement applies to a consequential change, or when I ask. If the project defines no such requirement, use it for changes that are risky, hard to reverse, or cross an interface boundary. Do not add ceremonial duplicate reviews to trivial changes.
- **Publishing (`shipper`):** Use it when I have asked to commit, push, or open/update a PR and the implementation, checks, and required review are complete. Hand it the files in the change, the verification run, and the PR scope; print the PR link in your final reply. Small follow-up Git operations can remain with the lead. The shipper does not merge PRs or fix source.

Model and effort for each role live in the agents' frontmatter under `.claude/agents/`, generated from `.claude/subagent-roles.conf`. They are defaults for cost-aware task routing, not mandates to use a particular main-session model.
